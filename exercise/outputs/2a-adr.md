# ADR-0002: แยกงานหลังวางคำสั่งซื้อด้วยเหตุการณ์

- **Status:** Proposed
- **Date:** 2026-10-27
- **Deciders:** ยังไม่ระบุ

## Context and problem

เมื่อมีการวางคำสั่งซื้อ ระบบต้องดำเนินการหลังการสั่งซื้อสามอย่าง:

- ส่งอีเมลยืนยันผ่าน MailFast ซึ่งเป็นผู้ให้บริการอีเมลภายนอก และแทนที่ logic ของ `emailservice` แบบ mock
- มอบ loyalty points ผ่าน `loyaltyservice` ใหม่
- บันทึกเหตุการณ์ "order placed" ให้ทีมการตลาด

ปีหน้าอาจมีงานหลังสั่งซื้อเพิ่มเติม เช่น SMS, fraud scoring และการอัปเดต recommendations จึงต้องเลือกวิธีเชื่อมโยงการวางคำสั่งซื้อกับงานเหล่านี้ โดย requirement ยังไม่ได้ระบุปริมาณงาน ข้อกำหนดด้านเวลา ความทนทานต่อความล้มเหลว หรือเทคโนโลยีที่ต้องใช้

## Decision drivers

- รองรับการเพิ่มงานหลังสั่งซื้อใหม่โดยลดการเปลี่ยนแปลงในขั้นตอนวางคำสั่งซื้อ (ความสามารถในการปรับเปลี่ยน)
- ลดการพึ่งพาความพร้อมใช้งานของผู้ให้บริการและงานปลายทางต่อการวางคำสั่งซื้อ (ความพร้อมใช้งาน)
- ทำให้การส่งอีเมล การให้คะแนน และการบันทึก analytics ดำเนินการได้อย่างเชื่อถือได้ โดยไม่ทำซ้ำผลข้างเคียง (ความน่าเชื่อถือและความถูกต้องของข้อมูล)
- ส่งอีเมลผ่าน MailFast ตาม requirement (การทำงานได้ตามข้อกำหนด)

## Considered options

1. ให้ขั้นตอนวางคำสั่งซื้อเรียก MailFast, `loyaltyservice` และระบบ analytics โดยตรงแบบ synchronous
2. เผยแพร่เหตุการณ์ "order placed" หลังวางคำสั่งซื้อ แล้วให้ผู้รับแยกกันจัดการอีเมล, loyalty points และ analytics
3. ใช้แนวทางผสม: ให้ขั้นตอนวางคำสั่งซื้อเรียกงานที่จำเป็นทันที และเผยแพร่เหตุการณ์สำหรับงานอื่น

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1. เรียกปลายทางโดยตรงแบบ synchronous | เส้นทางการทำงานตรงไปตรงมา; มองเห็นผลลัพธ์หรือข้อผิดพลาดจากปลายทางได้ทันที (ความเข้าใจง่าย) | การวางคำสั่งซื้อขึ้นกับความพร้อมใช้งานและ latency ของปลายทางทั้งหมด; การเพิ่มงานในอนาคตทำให้ขั้นตอนสั่งซื้อเชื่อมโยงกับบริการมากขึ้น (ความพร้อมใช้งาน, ประสิทธิภาพ, ความสามารถในการปรับเปลี่ยน) |
| 2. เผยแพร่เหตุการณ์และให้ผู้รับจัดการแยกกัน | แยกผู้เผยแพร่เหตุการณ์ออกจากงานปลายทาง; เพิ่มผู้รับใหม่ได้โดยไม่เพิ่มการเรียกตรงจากขั้นตอนสั่งซื้อ (ความสามารถในการปรับเปลี่ยน); ลดการรอ MailFast และระบบ analytics ในเส้นทางตอบกลับการวางคำสั่งซื้อ (ประสิทธิภาพ, ความพร้อมใช้งาน) | ต้องมีระบบรับส่งเหตุการณ์และการจัดการ retry; อาจเกิดการส่งซ้ำหรือความล่าช้าก่อนงานปลายทางเสร็จ (ความน่าเชื่อถือ, ความสอดคล้องของข้อมูล); เพิ่มองค์ประกอบและภาระปฏิบัติการ (ต้นทุน) |
| 3. แนวทางผสม | เลือกทำงานบางอย่างทันทีและเลื่อนงานอื่นได้; อาจตอบสนองกรณีที่ต้องการผลทันทีได้ (ประสิทธิภาพ) | ต้องกำหนดว่างานใดอยู่ในแต่ละเส้นทาง; เพิ่มความซับซ้อนและอาจสร้างรูปแบบความล้มเหลวที่แตกต่างกันต่อแต่ละงาน (ความสามารถในการปรับเปลี่ยน, ความน่าเชื่อถือ) |

## Decision

เสนอให้เลือก Option 2: หลังยืนยันการวางคำสั่งซื้อ ให้เผยแพร่เหตุการณ์ "order placed" และให้ผู้รับแยกกันดำเนินการส่งอีเมลผ่านการเชื่อมต่อ MailFast, มอบ loyalty points ผ่าน `loyaltyservice` และบันทึก analytics สำหรับทีมการตลาด

แนวทางนี้ลดการผูกงานที่กำลังจะเพิ่มในอนาคตเข้ากับขั้นตอนวางคำสั่งซื้อโดยตรง อย่างไรก็ตาม ก่อนนำไปใช้ต้องกำหนดกลไกการรับส่งเหตุการณ์และการรับประกันการส่งให้เหมาะกับข้อกำหนดด้านความทนทานต่อความล้มเหลวที่ยังไม่ระบุ การตัดสินใจนี้ยังไม่กำหนด protocol, message broker หรือการรับประกันการประมวลผล

## Consequences

- **Positive:** เพิ่มงานหลังสั่งซื้อ เช่น SMS หรือ fraud scoring ได้โดยเพิ่มผู้รับเหตุการณ์ แทนการเพิ่มการเรียกตรงในขั้นตอนวางคำสั่งซื้อ (คุณภาพ: ความสามารถในการปรับเปลี่ยน)
- **Positive:** ความล่าช้าหรือความไม่พร้อมใช้งานของ MailFast และระบบ analytics ไม่จำเป็นต้องทำให้เส้นทางตอบกลับการวางคำสั่งซื้อรอปลายทางเหล่านั้น (คุณภาพ: ประสิทธิภาพและความพร้อมใช้งาน)
- **Negative:** ผู้ใช้หรือระบบปลายทางอาจเห็นผลของงานหลังสั่งซื้อภายหลังจากการยืนยันคำสั่งซื้อ (คุณภาพ: ความสดใหม่ของข้อมูลและประสบการณ์ผู้ใช้)
- **Negative:** ต้องดูแลโครงสร้างพื้นฐานรับส่งเหตุการณ์และการติดตามผู้รับหลายตัว (คุณภาพ: ต้นทุนและความสามารถในการปฏิบัติการ)
- **Risks and mitigations:** การ retry อาจทำให้ส่งอีเมลซ้ำหรือให้ loyalty points ซ้ำ; กำหนดวิธี deduplicate หรือ idempotency สำหรับผู้รับแต่ละตัว และติดตามเหตุการณ์ที่ประมวลผลไม่สำเร็จ (คุณภาพ: ความถูกต้องของข้อมูลและความน่าเชื่อถือ) รายละเอียดกลไกและเป้าหมายการส่งมอบยังต้องตัดสินใจ

## Validation

- ทดสอบว่าวางคำสั่งซื้อแล้วเกิดเหตุการณ์ "order placed" และผู้รับที่กำหนดดำเนินการทั้งสามงานได้
- ทดสอบการ retry และการรับเหตุการณ์ซ้ำ เพื่อยืนยันว่าไม่เกิดการส่งอีเมลหรือให้คะแนนซ้ำโดยไม่ตั้งใจ
- ทดสอบเมื่อ MailFast หรือผู้รับรายใดรายหนึ่งไม่พร้อมใช้งาน ว่าการวางคำสั่งซื้อและการประมวลผลภายหลังเป็นไปตามข้อกำหนดที่ทีมตกลง
- ตรวจสอบว่าสามารถเพิ่มผู้รับงานหลังสั่งซื้อใหม่ได้โดยไม่ต้องเพิ่มการเรียกตรงจากขั้นตอนวางคำสั่งซื้อ
- กำหนดตัวชี้วัดและเกณฑ์ผ่านหลังจากตกลง SLO และความคาดหวังด้านการส่งมอบแล้ว

## Open questions

- ระบบรับส่งเหตุการณ์หรือ message broker ที่อนุมัติแล้วคืออะไร และใครเป็นผู้ดูแล?
- เหตุการณ์ต้องถูกเก็บไว้อย่างไร และต้องรับประกันการส่งหรือการประมวลผลในระดับใด?
- การยืนยันคำสั่งซื้อควรรอการเผยแพร่เหตุการณ์ หรือการบันทึกเหตุการณ์ต้องทำร่วมกับการบันทึกคำสั่งซื้อแบบ atomic หรือไม่?
- MailFast มี API, protocol, authentication, rate limit และนโยบาย retry ใดบ้าง?
- `loyaltyservice` มี API และกติกาป้องกันการให้คะแนนซ้ำอย่างไร?
- ระบบ analytics ปลายทางคืออะไร และรูปแบบ event/schema ที่ทีมการตลาดต้องการเป็นอย่างไร?
- เมื่อผู้รับล้มเหลวเกินจำนวน retry ที่กำหนด ต้องแจ้งเตือน กู้คืน หรือให้ผู้ปฏิบัติการจัดการอย่างไร?
- ต้องรองรับปริมาณงาน, latency, SLO หรือ retention เท่าใด?
- ทีมมีทักษะและข้อจำกัดด้านปฏิบัติการของระบบ messaging แบบใด?
